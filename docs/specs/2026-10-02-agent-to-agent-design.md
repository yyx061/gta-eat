# 设计：AI 对 AI 问店（方案 A：代理店家 AI）

状态：草稿，等确认后再动手。日期：2026-10-02。

## 1. 要解决什么

用户在「随便吃」看到几家候选，还拿不定主意。点一下「问问这几家」，我们的**找饭 AI** 就替用户去问每家店的 **店家 AI**：
现在能不能坐下、要不要订位、该点什么、合不合我今天的要求。几秒后给出排好序的结果，每家一句一针见血的理由。

现在没有真实的餐厅 AI 可接，所以每家店的 AI 先由我们**代建**（用我们已有的数据回答）。两边按公开的 **A2A 标准**说话，
以后哪家店有了自己的 AI，只要把那家的地址换成它的，其他都不用改。

## 2. 整体结构

```
手机 App（GitHub Pages，静态，不变）
   │  POST /ask   （需求 + 场合 + 候选 5 家 + 手机上已有的 Google 信息）
   ▼
小服务器（Deno Deploy，免费）  ── 代码放在仓库 agent/ 目录，push 后自动部署
   ├─ 找饭 AI（concierge）
   │     ├─ 并行用 A2A 问 5 家店家 AI（每家最多等 8 秒）
   │     └─ 汇总：排序 + 每家一句理由 + 「为什么不是别的」
   ├─ 店家 AI × 每家店   /a2a/store/{店ID}
   │     ├─ 名片：/a2a/store/{店ID}/.well-known/agent-card.json
   │     └─ 只根据「它自己的资料」回答，不知道就说不知道
   └─ 店家目录  /a2a/stores?near=纬度,经度   （以后真实餐厅 AI 在这里登记）
   │
   └─ DeepSeek（单独账号的 key，只存在服务器的环境变量里）
```

- **候选从哪来**：沿用手机上现有的推荐排序，取前 5 家去问。不让 AI 在 2.8 万家里乱找，费用和速度都可控。
- **店家资料从哪来**：服务器启动时从 GitHub Pages 读同一份 `food-data.js` / `site-data.js`（公开数据，不另存一份），
  再加上手机随请求带来的 Google 信息（评分、营业状态、营业时间；以后加「能否订位」和评论摘要）。
  服务器**不放 Google key**，不会多用 Google 额度。

## 3. 两边怎么说话（A2A）

- 按 A2A 规范的最小子集实现：**名片**（Agent Card）+ **message/send**（JSON-RPC 2.0 over HTTP）。
  不做流式、推送、长任务。规范升级时只改一层适配代码。
- 找饭 AI 发给店家 AI 的消息：一段文字问题 + 一个结构化部分：

```json
{ "need": "4 个人，想吃辣，30 分钟内坐下", "when": "周五 19:10", "weather": "雨 4°C",
  "party": 4, "arriveInMin": 12, "googleFacts": { "rating": 4.6, "count": 1200, "openNow": true, "closesAt": "22:30" } }
```

- 店家 AI 回复：一句文字 + 结构化答案（每条事实都标来源，没有来源的不许说）：

```json
{ "canSeat": "likely",            // yes / likely / unknown / closed
  "openUntil": "22:30",
  "reservation": { "reservable": "unknown", "advice": "周五晚高峰，4 个人建议先打电话", "link": "" },
  "waitGuess": { "level": "maybe", "basis": "周五晚饭 + 评论 1200 条，估计" },
  "mustOrder": [ { "dish": "水煮鱼", "source": "官网菜单" } ],
  "fit": { "score": 0.8, "because": "川菜，有你要的辣，走路 6 分钟" },
  "caveats": [ "不接受订位信息未知" ],
  "sources": [ "Google", "官网", "OSM" ] }
```

## 4. 店家 AI 怎么回答

- 一次 DeepSeek 调用。提示词只给它这家店的资料 + 问题，规则：
  - 只能用给到的资料；不知道就填 `unknown`，**不许编**等位时间、订位情况和菜名。
  - 「要等多久」只能给估计档位（不用等 / 可能要等 / 多半要等），并写明依据。
  - 用户说「不吃辣 / 素食」等硬条件不满足时，直接说不合适。
- AI 返回格式不对或超时：改用规则从资料直接拼一个答案（营业到几点、招牌菜、评分），保证总有回复。

## 5. 找饭 AI 怎么汇总

- 收齐回复后再调用一次 DeepSeek，输出：
  - 排序（先看能不能吃上、合不合要求，再看口味和距离）；
  - 每家**一句**理由，必须含一个具体事实（菜名 / 数字 / 你自己的记录），不超过约 30 个字；
  - 第一名额外一句「为什么不是第二名」。
- 只给 AI 用户画像的简短摘要（喜欢 / 不吃的菜系、预算、辣度），**不发**历史记录原文和 Uber 数据。

## 6. App 里怎么展示

- 「随便吃」结果下面加按钮 **「问问这几家」**，旁边可选人数（1 / 2 / 3–4 / 5+）和一个可选输入框「还有什么要求？」。
- 点了以后显示对话过程：「正在问 5 家店…」，每家店的回答到了就逐条出现（能看到 AI 对 AI 在问什么、答什么）。
- 全部回来后卡片重新排序，每张卡显示：一句理由、能否坐下 / 订位建议、推荐点什么，以及「打电话」「打开 Google 地图」按钮。
- 服务器连不上：提示「暂时问不到，先看本地推荐」，App 其他功能照常。

## 7. 安全和费用控制

- 服务器只接受来自 `yyx061.github.io` 的请求（CORS）。
- 用 Deno 自带的小数据库（Deno KV）计数：全站每天最多 **40 次「问问」**、店家 AI 每天最多 300 次调用，超了当天停用。
- DeepSeek 用**单独账号**，只充少量钱；key 只放在 Deno Deploy 的环境变量里，不进代码、不进网页。
- 预计每次「问问」约 0.3–0.5 美分；每天 10 次约每月 1 美元。

## 8. 以后怎么接真实餐厅 AI

- 店家目录里每家店有一条 `agentUrl`。默认指向我们代建的那个；餐厅有了自己的 A2A AI，就把这条改成它的地址。
- 找饭 AI 只认 A2A 标准，不关心对面是代建的还是真的。
- 打电话方案（B）以后作为一个特殊的「店家 AI」接进来：答不出的问题转给它去打电话。

## 9. 这一版不做

- 打电话、替你下单或订位、实时等位数字、餐厅认领页面（方案 C）。
- 「找一家」和「收藏」页面先不加按钮，先在「随便吃」试用。

## 10. 需要你做

1. 用 GitHub 登录 Deno Deploy（免费，不绑卡），把项目连到 `yyx061/gta-eat` 仓库，入口文件 `agent/main.ts`。
2. 新注册 DeepSeek 账号，充最低额度，key 放进 `.env` 的 `DEEPSEEK_AGENT_KEY`；我再教你填到 Deno Deploy 的环境变量里。

## 11. 怎么测试

- 本机装 Deno 跑服务器；用 curl 取名片、发 message/send，检查回答格式和「不编造」规则（给一家没有菜单的店，必须答不知道）。
- 无头浏览器测 App：模拟服务器正常、超时、出错三种情况，检查卡片排序、理由显示和退回本地推荐。
- 上线后真机试 5 次，看理由是否具体、速度（目标 10 秒内）和每次花费。
